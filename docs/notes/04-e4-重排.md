# 04 · E4：重排（唯一变量是是否重排）

## 口径

切片 `hierarchical`、检索 `hybrid` 均与 E3 相同，只把 `retrieval.rerank.enabled` 打开。索引不重建。

| 项 | 取值 |
| --- | --- |
| 实现 | `ApiCrossEncoderReranker` |
| 模型 | `gte-rerank-v2`（服务端 `/rerank` 端点） |
| 候选池 `top_n` | 20（融合后实际约 13–15 条） |
| 最终条数 | 5 |

## 结果

| 指标 | E3 无重排 | E4 有重排 | 变化 |
| --- | --- | --- | --- |
| Recall@5 | 0.9857 | 0.9857 | **持平** |
| HitRate@3 | 0.9286 | 0.9714 | **+4.3pp** |
| 可追溯率 | 0.9571 | 0.9714 | +1.4pp |
| 误拒 | 0.0286（2 条） | 0.0286（2 条） | 持平 |
| 误引 | 0.0143（1 条） | **0.0000（0 条）** | −1 条 |
| 单文档 / 跨文档 | 0.9833 / 1.0000 | 0.9833 / 1.0000 | 持平 |
| 延迟 p50 / p95 | 4405 / 6661 | 5697 / 7372 | **p50 +29%** |

## Recall@5 为什么一动不动

这不是重排失效，是 design 5.3 节预见过的第一种情况：

> 候选集质量已经很高：如果 top-5 里已经有正确片段，重排只是改变顺序，对 Recall@5 无贡献。

E3 时 Recall@5 已到 0.9857（69/70），只剩 1 条没召回。重排是在**已有候选内部重排序**，它无法召回融合阶段没进来的那条。指望它提升 Recall@5 本身就是看错了维度。

## 重排真正兑现的是另外两项

**HitRate@3 +4.3pp**：正确片段被提得更靠前。这一项在 `top_k` 较小时才有意义——如果下游只用前 3 条，这 4.3pp 就是实打实的；如果像本项目这样取 5 条喂给 LLM，收益就体现不出来。

**误引归零**：这是最值得记的一项。误引的定义是「没拒答、带了引用角标、但引的不是答案所在片段」——界面上是一份看着完全正常的答案配一排绿角标，客服会照着错的赔付标准去执行。它是这套系统里唯一「看不见」的失败，产品风险高于误拒。重排把它从 1 条压到 0 条。

代价是延迟 p50 涨 29%（4405 → 5697 ms）。这条要说清楚：重排需要额外一次网络往返，且候选 20 条要分两批请求。

**所以结论不能写成「重排无效」。** 它在 Recall@5 上无贡献，在 HitRate@3 与误引上有贡献，在延迟上有代价。design 5.3 要求「不要只看总指标」，这条提醒在这里直接决定了结论的对错。

## 选型变更记录（design 第 7 节要求）

design 原定的 provider 是 `bge_local`（本地 cross-encoder），**实际改用了服务端 `/rerank` 端点**，理由如下：

| 方案 | 否决原因 |
| --- | --- |
| `bge_local` | 要引入 torch 与 sentence-transformers，体积以 GB 计。本项目其余依赖全是轻量库，为一组对照实验赔掉「换台机器能一键跑起来」不划算 |
| LLM 打分（design 第 7 节的退路） | 它不是 cross-encoder。让聊天模型读候选再输出排序是 listwise 提示工程，各候选之间没有可比分数；而 5.3 节论证重排价值时的论据恰恰是「query 与文档拼成一个序列，交互更充分」。用它测出的结论回答不了原本提出的问题 |
| **服务端 `/rerank`** | 真正的 cross-encoder，零本地依赖、零额外体积。实测中文打分正确且区分度好（正确文档 0.94 vs 干扰项 0.24 / 0.009） |

## 实现中踩到的两个坑

**一，密钥路径走了岔路。** 初版在 `__init__` 里 `os.getenv("LLM_API_KEY")`，构造直接失败——项目的 `Secrets` 是 pydantic-settings 从 `.env` 读的，**不会写回环境变量**。改为由装配处注入 `api_key`，与 embedding / llm 两个 provider 走同一条路径。「密钥从哪来」这种问题不该有两个答案。

**二，服务端单次最多接受 10 个文档。** 实测：

```
请求  8 个 → 返回  8 个
请求 10 个 → 返回 10 个
请求 11 个 → 返回 10 个  << 被截断
请求 20 个 → 返回 10 个  << 被截断
```

**且不报错。** 不处理的话，配置写 `top_n=20`，实际参与竞争的却只有前 10 条——而界面、指标、日志全都看不出来。改为分批请求后，8/10/15/20 条候选都能拿全分数。

这个坑是被实现里那行 `log.warning` 抓到的（首次验证时打出「只返回 10/13 条候选的分数」）。如果图省事没写这行日志，它会安静地待到评测跑完，变成一份看似正常、实则候选池被腰斩的数据。

分批不影响分数可比性：cross-encoder 对每个 `(query, doc)` 独立前向传播，分数只取决于这一对，不像某些 embedding 那样在批内做统计量归一化。

## 什么时候值得加重排

- 只看 Recall@5：**不值得**（持平，还慢 29%）
- 下游只取前 3 条：**值得**（HitRate@3 +4.3pp）
- 把「假引用」当作不可接受的风险：**值得**（误引归零）
- 延迟预算紧张：不值得

本项目最终保留它，理由是第三条——假引用的代价是客服按错的赔付标准执行，那不是延迟能换回来的东西。
