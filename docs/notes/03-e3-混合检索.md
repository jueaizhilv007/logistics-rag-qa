# 03 · E3：混合检索（唯一变量是检索策略）

## 口径

只改一处：`retrieval.mode` 由 `vector` 改为 `hybrid`（BM25 + 向量，RRF 融合，`rrf_k=60`）。切片仍是 hierarchical，**索引不重建**——这是与 E2 的操作差异，也是为什么这一组能在不花 embedding 成本的前提下复跑。

## 结果

| 指标 | E2 `hierarchical+vector` | E3 `hierarchical+hybrid` | 变化 |
| --- | --- | --- | --- |
| Recall@5 | 0.9000 | **0.9857** | +8.6pp |
| HitRate@3 | 0.8000 | 0.9286 | +12.9pp |
| 可追溯率 | 0.8571 | 0.9571 | +10.0pp |
| 误拒 | 0.0714（5 条） | 0.0286（2 条） | −3 条 |
| 误引 | 0.0714（5 条） | 0.0143（1 条） | −4 条 |
| 单文档 | 0.9167 | 0.9833 | +6.7pp |
| 跨文档 | 0.8000 | **1.0000** | **+20pp** |
| 延迟 p50 / p95 | 4267 / 7433 | 4405 / 6661 | 基本持平 |

## E2 的推测在这里被验证

E2 里跨文档掉了 10pp，当时推测是「块变小后每条信息量下降，5 个位置凑不齐多家」。这一组引入 BM25 后，**跨文档回到 1.0000**——推测由此站住。

BM25 恰好补的是这个缺口：它按精确词项召回，不受块长度影响，「公司名 + 金额」这类组合即使落在小块的末尾也能被拉上来。向量路则相反，它依赖整块的语义平均，块越小、越是单一话题，反而越难兼顾"多家"这个需求。

延迟基本持平这点值得一提：BM25 是本地索引（jieba 分词 + rank-bm25），不额外调 API，代价只在首次检索时建一次倒排。

## 这组数据最值钱的部分：边际递减

`summary.csv` 里还有一行 `fixed+hybrid`（0.9571），是 S5 阶段为验证切片修复跑的。把四行摆在一起：

| 改动 | 在哪种基线上 | Recall@5 变化 |
| --- | --- | --- |
| 加 BM25 | fixed（E1 → `fixed+hybrid`） | 0.7714 → 0.9571，**+18.6pp** |
| 加 BM25 | hierarchical（E2 → E3） | 0.9000 → 0.9857，**+8.6pp** |
| 换层级切片 | vector（E1 → E2） | 0.7714 → 0.9000，**+12.9pp** |
| 换层级切片 | hybrid（`fixed+hybrid` → E3） | 0.9571 → 0.9857，**+2.9pp** |

**同一项改动，加在弱基线上收益大、加在强基线上收益小。** 这不是某套方案更好的证据，而是「两者补的是同一个缺口、从不同方向」的证据——标题链让每块自带归属信息，BM25 让精确词项不被语义平均稀释，它们各自都能把 E1 那 17 条误拒压下去，因此叠在一起时收益自然变小。

如果只看一条数据（比如「层级切片 +12.9pp，混合检索 +18.6pp，所以用混合检索」），就会得出一个完全站不住的结论。这是四组实验值得做、而不是只挑最优配置的原因。
