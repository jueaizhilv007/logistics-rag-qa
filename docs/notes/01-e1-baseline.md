# 01 · E1 baseline：固定切片 + 纯向量

## 口径

| 项 | 取值 |
| --- | --- |
| 切片 | `fixed`，size 500 / overlap 50 |
| 检索 | `vector`（cosine） |
| 重排 | 否 |
| top_k | 5 |
| 索引 | 168 块 |

`config.yaml` 里 `retrieval.mode` 的默认值必须是 `vector`，这是 design 的硬性要求：baseline 若默认开着 BM25，E2 以后的每一步就都无法单独归因到「换个检索策略」上。评测命令因此也显式传 `--mode vector`，不依赖默认值。

E1 的全部意义是当尺子。它本身不是一个「应该被采用的配置」。

## 结果

| 指标 | 值 |
| --- | --- |
| Recall@5 | 0.7714（54/70） |
| HitRate@3 | 0.6857（48/70） |
| 可追溯率 | 0.6857（48/70） |
| 误拒率-可答题 | 0.2429（17 条） |
| 误引率 | 0.0714（5 条） |
| Recall@5 单文档 | 0.7500（60 条） |
| Recall@5 跨文档 | **0.9000**（10 条） |
| 延迟 p50 / p95 | 3711 / 5036 ms |

## 两个不能只看总数的地方

**失败几乎全在误拒（17 条），而不是误引（5 条）。** 这意味着失败是「看得见的」：界面弹拒答框，客服转人工。它当然糟糕，但不会误导人——不像误引那样给出一份看着正常的答案却配着错的引用角标。后面几组的改善也主要发生在这个分项上。

**跨文档 0.90 反而高于单文档 0.75。** 这与 S5 里得到的印象相反——那条结论是「跨文档失败率是单文档的 6 倍」，但它是基于 `fixed+hybrid` 得出的，不是 baseline。

## 为什么纯向量下跨文档反而更准

推测：跨文档题的问法通常是「各家快递的赔付上限分别是多少」，句中直接出现多家公司名与「上限」「多少钱」这类词，特征明显，向量路不难匹配到对应文档。而单文档题多是「XX 情况下怎么赔」，要的是精确条款定位，语义相近但不适用的片段（比如另一家公司的同名条款）很容易被一起召回，挤掉正确那条。

这条推测在 [03](./03-e3-混合检索.md) 里被验证了：BM25 加进来之后，涨的正是单文档那一侧。

这条也提醒了一件事：**分层数据必须标明它是在哪套配置下测的**。同一份评测集，「谁更难」会因为检索策略而反转，脱离配置谈瓶颈会指错方向。
